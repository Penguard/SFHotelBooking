# Архитектурные решения (ADR)

Здесь зафиксированы ключевые решения реализации и их ограничения. Подробные маршруты API и инструкция запуска приведены в [основном README](../README.md).

## ADR-001 — Четыре независимых сервиса

**Решение:** Eureka Server, реактивный API Gateway, Hotel Service и Booking Service являются самостоятельными Spring Boot приложениями в одном Maven-проекте. Общий Java-модуль не используется; небольшие классы конфигурации безопасности и обработки ошибок находятся в соответствующих сервисах.

**Компромисс:** небольшое дублирование кода вместо дополнительной зависимости между сервисами.

## ADR-002 — Отдельные H2 и таблица интервалов занятости

**Решение:** Booking и Hotel используют независимые in-memory БД. Booking хранит идентификаторы отеля и номера без межсервисных JPA-связей. Hotel хранит отдельные записи `room_slots` со статусами `ACTIVE` и `RELEASED` и уникальным `booking_id`.

**Причина:** доступность на полуоткрытом интервале `[startDate, endDate)` определяется активными слотами, а `rooms.available` отражает эксплуатационную доступность номера. Записи `RELEASED` позволяют отклонять запоздавшее подтверждение уже отменённого бронирования.

**Ограничение:** H2 в памяти теряет данные при перезапуске и не подходит для долговременного хранения броней.

## ADR-003 — Сага на локальных транзакциях

**Решение:** Booking фиксирует `PENDING`, вызывает Hotel для резервирования и затем фиксирует `CONFIRMED`. При ошибке сохраняет `CANCELLED` и вызывает компенсацию `release`. Если освободить слот не удалось, сохраняется `release_pending=true`. Планировщик повторяет компенсации каждые 10 секунд и обрабатывает `PENDING` старше 60 секунд.

**Причина:** согласование двух сервисов без распределённой XA/2PC-транзакции.

**Ограничение:** во время сбоев возможна временная несогласованность. Для промышленной эксплуатации потребовались бы постоянная БД и надёжный механизм доставки/повтора событий, например transactional outbox.

## ADR-004 — Конкурентность и идемпотентность

**Решение:** на `bookings.request_id` и `room_slots.booking_id` установлены ограничения уникальности. Hotel блокирует строку номера через `PESSIMISTIC_WRITE` перед проверкой пересечений и созданием слота. Повторы используют те же `bookingId` и `requestId`; повторная компенсация не изменяет статистику повторно.

**Причина:** защита от двойных броней при одновременных запросах без локальных Java-мониторов.

**Ограничение:** пока первоначальный запрос обрабатывается, повтор может получить `202 PENDING`. Автоподбор выбирает номер по снимку доступности; при конфликте система отвечает `409` и не пытается автоматически выбрать следующий номер.

## ADR-005 — Доверие между сервисами на основе JWT

**Решение:** Booking выпускает HS256 JWT; Gateway, Booking и Hotel проверяют подпись и срок действия. Для пользователей предусмотрены роли `USER` и `ADMIN`, для внутренних операций с интервалами — `SERVICE`. Проверка прав реализована также через `@PreAuthorize`; Gateway закрывает внутренние маршруты резервирования.

**Компромисс:** единый симметричный ключ упрощает демонстрацию, но любой сервис с этим ключом технически способен выпускать токены. Для внешнего развёртывания нужны управление секретами, HTTPS и предпочтительно асимметричная подпись с ключом выдачи только у авторизационного сервиса.

## ADR-006 — Ограниченные повторы и восстановление после сбоев

**Решение:** `RestClient` использует тайм-аут соединения 700 мс, чтения 1500 мс и до трёх попыток при сетевых сбоях и HTTP 5xx с экспоненциальной задержкой. Вызов подтверждения защищён CircuitBreaker. Компенсация `release` обходит CircuitBreaker, чтобы недавние сбои не блокировали восстановление.

**Ограничение:** синхронный REST-вызов увеличивает задержку в условиях отказа Hotel Service. Для высокой нагрузки и долговременного хранения операций потребовалась бы более устойчивая асинхронная инфраструктура.
