# План тестирования Hotel Booking Microservices

Этот документ — **инструкция по проверке проекта**: какие требования покрывают автоматические тесты, как их запускать, как воспроизводить ключевые сценарии вручную и какие дополнительные проверки можно выполнить.

## 1. Что проверяется

Система состоит из четырёх запускаемых приложений:

| Приложение | Порт | Предмет проверки |
| --- | --- | --- |
| `eureka-server` | `8761` | Обнаружение и регистрация сервисов |
| `api-gateway` | `8080` | Внешняя точка входа и маршрутизация |
| `hotel-service` | `8081` | Отели, номера, доступность, учёт занятости |
| `booking-service` | `8082` | Пользователи, JWT, бронирования, Saga |

Проверка организована в три уровня: **автоматические тесты Maven**, **сквозной smoke-тест** через Gateway и **дополнительные ручные сценарии** (безопасность, аналитика, отказоустойчивость, наблюдаемость). Одни лишь модульные тесты не заменяют проверку связи работающих сервисов.

### Особенности тестовой среды

- Требуются JDK 17+ и Maven (можно использовать Maven, встроенный в IntelliJ IDEA).
- Базы Hotel и Booking — независимые **H2 in-memory**. При перезапуске соответствующего сервиса данные обнуляются, а демонстрационные записи создаются заново. Не следует использовать эту конфигурацию для проверки долговременной сохранности данных.
- В `booking-service` удалённый Hotel Service в автоматических тестах заменяется mock-объектом/имитацией HTTP-вызова; реальный обмен через Eureka и Gateway проверяется отдельно.
- Используйте тестовые учётные записи и секреты из конфигурации локального окружения. Не публикуйте в скриншотах JWT и пароли.

## 2. Как запустить автоматические тесты

Откройте терминал **в корне проекта** (рядом с `pom.xml`):

```powershell
mvn clean verify
```

Можно запустить сборку без очистки:

```powershell
mvn verify
```

Чтобы проверить только один модуль:

```powershell
mvn -pl hotel-service -am test
mvn -pl booking-service -am test
```

Чтобы запустить определённый тестовый класс (из корня):

```powershell
mvn -pl hotel-service -Dtest=HotelServiceTest test
mvn -pl booking-service -Dtest=BookingWorkflowEdgeCasesTest test
mvn -pl booking-service -Dtest=HotelHttpClientTraceTest test
```

**Ожидаемое поведение:** Maven завершится с `BUILD SUCCESS`; все тесты должны иметь `Failures: 0`, `Errors: 0`. В текущем комплекте тестов — **22 проверки**: 6 в Hotel Service и 16 в Booking Service. Это ориентир для проверки состава, а не заранее гарантированный результат будущих запусков.

Отчёты сохраняются в `hotel-service/target/surefire-reports/` и `booking-service/target/surefire-reports/`. Для диагностики ошибки найдите файл с именем упавшего тестового класса (`*.txt` или `TEST-*.xml`) и изучите stack trace. **Запуск четырёх приложений для `mvn verify` не нужен.**

## 3. Какие сценарии покрывают автоматические тесты

### 3.1. Hotel Service — `HotelServiceTest` (6 тестов)

| Тест | Что проверяется | Как трактовать успех |
| --- | --- | --- |
| `duplicateConfirmAndReleaseAreIdempotent` | Повторное подтверждение/освобождение одного слота | Повторный вызов не создаёт лишнюю резервацию и не нарушает состояние |
| `preemptiveReleasePreventsLateConfirm` | `release` приходит раньше задержавшегося `confirm` | Поздний `confirm` не захватывает освобождённый слот |
| `twoParallelBookingsOfSameDatesHaveOnlyOneWinner` | Два потока одновременно бронируют один номер на пересекающиеся даты | Не более одной успешной резервации, нет двойной брони |
| `concurrentNonOverlappingBookingsMayBothSucceed` | Два параллельных запроса на один номер, даты не пересекаются | Оба периода могут быть забронированы |
| `recommendationsAreOrderedByTimesBookedThenId` | Алгоритм рекомендаций | Сначала меньше `timesBooked`; при равенстве — меньший `id` |
| `permissionsAndValidationReturnCorrectStatuses` | Ограничения доступа и некорректные входные данные | Возвращаются предусмотренные HTTP-статусы |

**На что обратить внимание дополнительно:** успешный тест конкурентности проверяет определённый сценарий в рамках одного тестового окружения, а не производительность под произвольной нагрузкой.

### 3.2. Booking Service — `BookingServiceTest` (9 тестов)

| Тест | Что проверяется |
| --- | --- |
| `successfulBookingAndRepeatedDeliveryUseOneRow` | Создание `CONFIRMED` и повтор запроса с тем же ключом без новой брони |
| `serviceConflictCancelsAndCompensates` | Отмена при конфликте `409` и вызов компенсации |
| `timeoutCancelsAndKeepsPendingCompensationWhenReleaseAlsoFails` | Сбой Hotel Service и сохранение признака отложенной компенсации |
| `retryTaskCompletesCompensationWhenHotelRecovers` | Повторная попытка компенсации после восстановления Hotel Service |
| `autoSelectPicksLeastUsedRoomAndCancellationRetrySucceeds` | Автоподбор наименее используемого номера и повтор отмены |
| `onlyOwnerMayReadOtherUsersBooking` | Недоступность чужой брони обычному пользователю |
| `idempotencyKeyCannotBeReusedWithDifferentPayload` | Защита от использования одного ключа для разных параметров бронирования |
| `validationAndSecurity` | Базовая валидация запросов и авторизация |
| `missingIdempotencyHeaderReturnsBadRequest` | `400` без обязательного заголовка `X-Request-Id` |

### 3.3. Авторизация — `JwtAuthIntegrationTest` (1 тест)

`registrationIssuesRealJwtThatResourceServerAccepts` проверяет регистрацию, выпуск настоящего JWT и возможность использовать его при запросе к защищённому API; в рамках сценария проверяются также ошибки учётных данных и ограничения доступа.

### 3.4. Неочевидные сценарии Saga — `BookingWorkflowEdgeCasesTest` (3 теста)

| Тест | Что проверяется |
| --- | --- |
| `autoSelectConflictCurrentlyReturns409WithoutTryingNextRecommendedRoom` | **Текущее ограничение:** при `409` для первого рекомендованного номера сервис не пытается взять следующий |
| `compensationIsRetriedUntilHotelRecovers` | Неудачный `release` повторяется, а при восстановлении связи компенсация завершается |
| `stalePendingBookingIsCancelledAndCompensated` | Зависшее в `PENDING` бронирование отменяется с попыткой освобождения слота |

**Важно:** первый тест закрепляет *текущее* поведение, а не доказывает наличие перебора альтернатив. Если требование предусматривает автоматическую попытку следующего номера, нужно менять алгоритм и ожидаемый результат теста.

### 3.5. Корреляция HTTP-вызовов — `HotelHttpClientTraceTest` (3 теста)

| Тест | Что проверяется |
| --- | --- |
| `confirmPreservesIncomingTraceIdAcrossServiceRequest` | `X-Trace-Id` при вызове подтверждения слота |
| `releasePreservesIncomingTraceIdAcrossServiceRequest` | `X-Trace-Id` при освобождении слота |
| `recommendationsPreserveIncomingTraceId` | `X-Trace-Id` при запросе рекомендаций |

Тесты проверяют **исходящий HTTP-заголовок клиента Booking → Hotel**, подставляя значение в MDC. Они **не гарантируют** сквозную корреляцию Gateway → Booking → Hotel: она проверяется отдельно в разделе 6.6.

## 4. Подготовка к ручным проверкам

1. Запустите приложения в следующем порядке: `eureka-server`, `hotel-service`, `booking-service`, `api-gateway`.
2. Откройте `http://localhost:8761` и убедитесь, что нужные экземпляры Hotel Service, Booking Service и Gateway зарегистрированы как `UP`.
3. Откройте Swagger UI: Hotel — `http://localhost:8081/swagger-ui.html`; Booking — `http://localhost:8082/swagger-ui.html`.
4. Получите JWT через `POST /user/auth` (Swagger Booking Service) с тестовыми учётными данными, определёнными в конфигурации. Для административных операций нужен JWT пользователя с ролью `ADMIN`.
5. В Swagger нажмите **Authorize**, вставьте токен в формате, который требует поле авторизации, и выполните нужный запрос.

Если через Gateway поступает `503 Service Unavailable`, проверьте регистрацию сервисов в Eureka и их непосредственную доступность на портах `8081`/`8082`. `401` означает отсутствие/некорректность авторизации, `403` — недостаточные права. После запуска приложений может потребоваться небольшое время на регистрацию в Eureka.

Для всех запросов с датами используйте **будущие** даты; формат — `yyyy-MM-dd`, дата выезда позднее даты въезда. Не копируйте вечно фиксированные даты из старых демонстраций: со временем они станут прошедшими.

## 5. Сквозная проверка через API Gateway (smoke-test)

Запустите в корне проекта:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\demo.ps1
```

Скрипт использует будущие даты и проверяет последовательность:

1. Авторизация демонстрационного пользователя, получение JWT.
2. Поиск доступных номеров через Gateway.
3. Создание бронирования с `X-Request-Id`; ожидается `CONFIRMED`.
4. Повтор того же запроса с тем же `X-Request-Id`; ожидается **тот же ID бронирования**.
5. Создание пересекающегося бронирования с новым `X-Request-Id`; ожидается `409 Conflict`.
6. Отмена первой брони и получение истории; ожидается `CANCELLED`.

**Критерий прохождения:** терминал выводит `SMOKE TEST PASSED`. При ошибке смотрите точный шаг и HTTP-код; `503` обычно указывает на недоступность маршрута/сервиса, а не на ошибку бизнес-логики. Скрипт работает через `localhost:8080`, то есть проверяет связку из нескольких приложений.

## 6. Дополнительные ручные сценарии (как проверить)

### 6.1. Фильтрация и сортировка номеров

В Swagger Hotel Service выполните `GET /api/rooms/recommend` с будущими `startDate`, `endDate`.

- Проверьте, что все строки имеют `available=true`.
- Проверьте последовательность `timesBooked`: значения должны идти по возрастанию. При равенстве сравните `id`.
- Повторите запрос с `capacity=3`: останутся номера с `capacity >= 3`.
- Повторите запрос с `hotelId=1`: останутся номера только выбранного отеля.
- Создайте подтверждённую бронь на нужный период и повторите запрос: занятый номер не должен присутствовать в списке свободных на пересекающиеся даты.

Сопоставьте результат с `GET /api/rooms` (обычный перечень доступных номеров без рекомендательной сортировки). Набор данных может изменяться после бронирований и рестартов.

### 6.2. Статистика отеля и номера

Используйте **ADMIN JWT** в Swagger Hotel Service:

```text
GET /api/hotels/1/stats?startDate=YYYY-MM-DD&endDate=YYYY-MM-DD
GET /api/rooms/1/stats?startDate=YYYY-MM-DD&endDate=YYYY-MM-DD
```

Подставьте одинаковый будущий интервал. Проверьте поля `totalRooms`, `operationalRooms`, `occupiedRooms`, `totalTimesBooked`, `occupiedRoomDays`, `possibleRoomDays`, `occupancyPercent` для отеля; `timesBooked`, `activeReservations`, `occupiedDays`, `occupancyPercent` для номера.

**Проверка расчёта:** если у отеля 3 доступных для эксплуатации номера и интервал составляет 3 ночи (дата выезда не включается), `possibleRoomDays` должен составлять 9. Если заняты 3 номеро-дня, занятость — `3 / 9 * 100 = 33,33%` (с учётом округления API). Перед сравнением выясните, пересекаются ли активные резервации с указанными датами: `timesBooked > 0` не обязательно означает ненулевую занятость в данном интервале.

Для ручной проверки изменений выполните бронь, посмотрите статистику и затем отмените бронь. Сравните значения до и после. Не предполагайте, что исторический счётчик обязательно ведёт себя как количество активных слотов: проверяйте бизнес-правило, реализованное в сервисе.

### 6.3. JWT, роли и владение бронированиями

1. Выполните запрос к защищённому `GET /api/rooms` **без токена**: ожидайте `401`.
2. Отправьте тот же запрос с испорченным JWT: ожидайте `401`.
3. Авторизуйтесь как обычный `USER`; попробуйте `GET /api/hotels/1/stats`: ожидайте `403`.
4. Авторизуйтесь как `ADMIN`; повторите запрос статистики: ожидайте `200`.
5. Создайте бронь от пользователя A, затем попробуйте `GET /booking/{id}` от пользователя B: ожидайте запрет доступа (`403`); владелец и администратор должны иметь доступ согласно правилам Booking Service.
6. Попробуйте `POST /booking` без `X-Request-Id`, но с валидным JWT и телом: ожидайте `400`.

### 6.4. Конфликт, идемпотентность и даты

Через `POST /booking` (Swagger Booking Service или API Gateway) создайте бронь на будущий интервал. Обязательно передайте `X-Request-Id` — строку UUID, например сгенерированную в PowerShell:

```powershell
[guid]::NewGuid().ToString()
```

В теле запроса используйте поля `roomId`, `autoSelect`, `startDate`, `endDate` (сам ключ идемпотентности находится **в заголовке**, не в JSON).

Проверьте:

- Повтор **того же** запроса с тем же ключом: возвращается тот же `booking.id`.
- Повтор ключа с **другими** датами или номером: запрос отклоняется.
- Новая попытка брони того же номера на пересекающийся интервал с **новым** ключом: ожидается `409`.
- После отмены брони можно повторно забронировать освободившийся интервал.
- При `autoSelect=true` рекомендация выбирает наименее используемый номер; если первый выбранный номер становится занятым до подтверждения, текущий алгоритм может завершиться `409` **без перехода к следующему кандидату**. Для воспроизводимой проверки этого ограничения используйте автоматический `BookingWorkflowEdgeCasesTest`.

### 6.5. Отказоустойчивость Saga и компенсация

> **Внимание:** это разрушающий для тестовых данных сценарий — перезапуск Hotel Service очищает его H2 in-memory. Выполняйте только в демонстрационном окружении.

1. Убедитесь, что все сервисы работают, и получите JWT USER.
2. Остановите **только Hotel Service** в IntelliJ. Booking Service, Eureka и Gateway оставьте запущенными.
3. Отправьте через Booking Service запрос бронирования на существующий номер с новым `X-Request-Id`.
4. Ожидайте ошибку доступности зависимости (обычно `503`); запрос может ждать из-за тайм-аутов и повторов.
5. По `GET /booking/{id}` или `GET /bookings` найдите возникшую запись: ожидается `CANCELLED`; пока release не выполнен, возможно `releasePending=true`.
6. В консоли Booking Service найдите события `CANCELLED`, `COMPENSATION_PENDING`.
7. Запустите Hotel Service заново, убедитесь в статусе `UP` в Eureka.
8. Проверьте консоль Booking Service: фоновый планировщик должен повторять `release`; ищите событие `COMPENSATED` для **того же** `bookingId`.
9. Повторите `GET /booking/{id}`: ожидается `status=CANCELLED`, `releasePending=false`.

Важная оговорка: `COMPENSATED` означает, что операция компенсации успешно выполнена с точки зрения Booking Service. Из-за H2 in-memory этот опыт **не доказывает восстановление прежних данных Hotel Service после рестарта**. Если попытка создания брони не сформировала запись, не придумывайте ID — сначала проверьте историю и логи.

### 6.6. Логи и прослеживаемость `traceId`

1. Запустите все четыре приложения. Откройте консоли Run для Gateway, Booking и Hotel.
2. Отправьте **один** запрос на создание бронирования через Gateway `http://localhost:8080` с JWT и новым `X-Request-Id`.
3. Посмотрите ответный HTTP-заголовок `X-Trace-Id` (если он возвращён данным маршрутом).
4. Найдите в консолях каждого участвующего сервиса записи, относящиеся к этому запросу. Сопоставьте `traceId` и `bookingId`.
5. Проверьте наличие структурных элементов записи: время, уровень, сервис/класс, событие, причина ошибки. Для ошибки проверьте запись уровня WARN/ERROR.

**Критерий сквозной корреляции:** один и тот же идентификатор должен обнаруживаться у взаимосвязанных запросов на всех фактически пройденных этапах. Если значения расходятся либо Gateway не логирует ID, фиксируйте это как ограничение сквозной трассировки. Автоматический `HotelHttpClientTraceTest` подтверждает только заголовки исходящих запросов клиента. В фоновой задаче без входящего запроса лог может содержать `[trace=]`; её записи сопоставляются по `bookingId`.

### 6.7. CRUD отелей и номеров

В Swagger Hotel Service с ADMIN-токеном создайте **новый тестовый отель** через `POST /api/hotels`, затем получите его через `GET /api/hotels/{id}`, измените через `PUT /api/hotels/{id}` и удалите через `DELETE /api/hotels/{id}`. Проверьте соответствующие `201`/`200`/`204` и что после удаления ресурс недоступен. Конкретные поля JSON и ограничения смотрите в схемах `HotelInput` внутри Swagger.

Аналогично проверьте CRUD номеров через `/api/rooms`. Удаление объектов, связанных с существующими слотами или бронями, может быть ограничено бизнес-правилами — тестируйте на **новых** записях без реальных резерваций. С токеном USER административные операции должны отклоняться (`403`).

### 6.8. Маршрутизация, восстановление и Docker (опционально)

- Сравните ответы одного и того же защищённого GET через Gateway (`localhost:8080`) и напрямую через целевой сервис (`8081` или `8082`).
- Остановите целевой сервис: проверьте, что Gateway не выдаёт ложный успешный ответ; после восстановления и регистрации в Eureka маршрут снова работает.
- Если используется Docker Desktop: подготовьте `.env` на основе `.env.example` (с собственными значениями секретов), выполните `docker compose up --build -d`, проверьте `docker compose ps`, затем `scripts/demo.ps1`; завершение — `docker compose down`.

## 7. Что ещё можно проверить при желании

| Дополнительный сценарий | Способ | Что выясняем |
| --- | --- | --- |
| Нагрузка 10–50 конкурентных запросов | Параллельные HTTP-запросы с разными UUID на один период | Отсутствие двойной брони, корректность отказов |
| Повторение после задержки сети | Управляемая имитация задержки Hotel Service | Пределы Retry, работа Circuit Breaker и компенсации |
| Границы дат | Прошедшая дата, равные даты, некорректный формат, слишком длинный период | Валидация и ожидаемые `400` |
| Некорректный `X-Request-Id` | Передать не-UUID | Обработка ошибки без создания брони |
| Массовая отмена и повторный `DELETE` | Отменить одну бронь дважды | Идемпотентность отмены и отсутствие лишних блокировок |
| Доступ к внутренним эндпойнтам Hotel | Вызвать `/api/rooms/{id}/release` с USER JWT | Запрет выполнения операций роли SERVICE |
| Изоляция данных пользователей | Истории двух USER-аккаунтов | Отсутствие утечки чужих броней |
| Проверка сброса H2 | Перезапустить один бизнес-сервис | Наглядно подтвердить ограничение демонстрационного хранения |

## 8. Критерии готовности к демонстрации

- `mvn clean verify` завершается с `BUILD SUCCESS`, без failures/errors.
- `scripts/demo.ps1` выдаёт `SMOKE TEST PASSED` при запущенных сервисах.
- Hotel Service показывает корректную сортировку, фильтрацию и расчёты статистики.
- Безопасность возвращает ожидаемые `401`/`403`, защищает чужие брони.
- Конкурентные запросы не приводят к двойному бронированию.
- При отказе Hotel Service состояние брони остаётся согласованным; ожидающая компенсация завершается после восстановления зависимости.
- По логам можно восстановить ход выполнения Saga; ограничения сквозного `traceId` описываются честно.
